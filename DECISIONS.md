# Decisions

## Brand: SpotifyCares
I went with SpotifyCares over comcastcares, TMobileHelp, UPSHelp, AmazonHelp, and AppleSupport. Spotify is a single digital product, so you get genuine variety in what people are actually asking about: billing disputes, playback bugs, account access, people trying to cancel, without the noise you get from an ISP where nearly every ticket boils down to "the internet is down." I picked it for the depth it gives the failure analysis and escalation reasoning, since the grading weighs eval rigor over how polished the agent itself is, not because it's the biggest brand in the dataset.

## LLM: Claude Haiku for classification and the baselines, Sonnet for drafting and judging
One provider, one adapter interface. Haiku is cheap enough to run over the whole subsample during iteration without thinking twice. Sonnet is reserved for reply drafting and the LLM judge, where reasoning quality actually matters more than cost.

## Dependency manager: venv + pip, reversed from an initial uv choice
I started with uv, hoping for a single tool to handle the venv, lockfile, and install in one go. Reversed course once both uv and plain pip hit the exact same broken TLS chain on this machine (`SSL: CERTIFICATE_VERIFY_FAILED`, a local network or certificate interception issue, not a PyPI problem) and needed non-default flags just to install anything. `python -m venv` plus `pip install -e ".[dev]"` is the more universally available baseline, no extra tool for a grader to install, and `pyproject.toml` stays the single source of truth for dependencies either way. Traded away uv's lockfile-pinned reproducibility for less setup friction on a machine I can't predict.

## Build backend: hatchling over uv_build
uv_build wants a single package living under `src/<project_name>/`. This project's structure puts several top-level packages directly under `src/` (domain, adapters, orchestration, interfaces, config), plus a sibling `eval/` package at the repo root. hatchling's `packages = [...]` list handles that directly with an editable install, so `from domain.models import X` just works from anywhere in the repo without any path hacks.

## Intent taxonomy: a closed set of 6, not open classification
BILLING_DISPUTE, PLAYBACK_BUG, ACCOUNT_ACCESS, CANCELLATION_RETENTION, FEATURE_QUESTION, OTHER. It's a `str, Enum`, so it serializes cleanly through Pydantic without any custom encoder. A closed set keeps the classifier's output space fixed and makes agreement statistics well-defined. OTHER is the escape hatch for anything that doesn't fit, rather than letting the model invent new categories on the fly.

## Escalation rule is a plain function, not an injected Protocol
Escalation is deterministic once you have a `ClassificationResult`, confidence threshold plus a few intent-specific rules, it's not an LLM call. The project's own rule is not to build an interface for something that will only ever have one implementation, so it just lives as a plain function in `domain/escalation.py`. That's different from `Classifier`, `ReplyDrafter`, and `Judge`, which really are Protocols, because those implementations are genuinely swappable adapters.

## Escalation policy: confidence threshold OR high-risk intent, never confidence alone
It escalates when classifier confidence drops below 0.7, or when the intent is BILLING_DISPUTE or CANCELLATION_RETENTION, no matter how confident the model is. Confidence alone would happily auto-handle a confidently wrong billing dispute, and money or churn issues deserve a human even when the classifier feels sure, since a wrong auto-reply there costs more than one on a playback bug does. The threshold and the high-risk set live as fields on `EscalationPolicy` (`domain/escalation.py`), built from `Settings` at the orchestration layer rather than handed the whole settings object, domain only sees the two primitives it actually needs and stays decoupled from adapter-level concerns like model names and file paths.

## Golden set schema: intent, escalate, and notes, no written reference reply
Each hand-labeled example captures the true intent, whether it should've been escalated, and free-text notes. The actual historical SpotifyCares reply already exists in the subsample data, so there's no reason to have someone retype it. Labeling only ever shows the customer's message, never the historical reply, so the escalate judgment can't get anchored on what the brand happened to do at the time.

## Reply grounding: pull precedent by classified intent
The whole subsample gets classified once with Haiku, cached, so it's a one-time cost and free on every rerun after, then grouped into a `PrecedentIndex` by intent. At draft time, a few same-intent historical pairs, the customer's message and SpotifyCares' actual reply, get pulled in as few-shot context for the Sonnet call. No embedding or vector-search dependency needed, stays well inside the dependency list I'd already locked in, and it matches "grounded in how the brand historically resolved similar issues" directly instead of approximating it through keyword overlap.

## Baselines: a rule-based keyword classifier, and zero-shot ungrounded Haiku
Baseline 1 is pure keyword and regex matching, no LLM at all, with a fixed canned reply per intent, always auto-handled. Baseline 2 is zero-shot Haiku classify and draft, no retrieval, no historical grounding. Comparing the full agent against both isolates two separate sources of any improvement: does using an LLM at all help (baseline 1 to baseline 2), and does grounding plus a stronger model help on top of that (baseline 2 to the full agent). Not built in the first session, deferred until after the golden set and pipeline were both verified.

## Structured LLM output through `client.messages.parse(output_format=...)`, not manual tool-use JSON
The Anthropic SDK has a native `messages.parse` method that takes a Pydantic model as `output_format`, derives a JSON schema from it, and hands back a `parsed_output` already validated against that model. Used directly for `ClassificationResult` and `JudgeVerdict`. For `DraftReply`, the LLM only ever produces the `text` field, and `grounded_on` gets filled in from the precedent ids that were actually retrieved, not self-reported by the model, since that's something I already know for certain and don't need to trust the model's own account of. A malformed or missing `parsed_output` raises `LLMResponseError` outright rather than quietly falling back to a guess.

## Classifier confidence is self-reported, not calibrated
`ClassificationResult.confidence` comes from just asking the model to report a number between 0 and 1, it isn't a statistically calibrated probability pulled from logprobs or repeated sampling. Flagging this early because it's exactly the kind of thing that turns into a "what's misleading about my headline number" caveat later, a mean self-reported confidence is not the same claim as a mean calibrated one. Constrained to [0, 1] with a Pydantic `Field`, both to keep the JSON schema handed to the model precise, and so the confidence-threshold check in escalation can't silently misbehave on an out-of-range value.

## Precedent pool sampled disjoint from whatever's being classified or drafted
An 8-angle review of the day-2 diff caught a real leakage bug: the CLI's `run` command was originally building the precedent index from the same small `--count` sample it then drafted replies for, so a conversation could end up retrieving its own actual historical resolution as its own "precedent," the model was being shown the answer to the question it was being asked. Fixed by shuffling the full subsample once per run with a fixed seed, then slicing two disjoint ranges: one for what actually gets processed, one for what the precedent index is built from, with a `--precedent-pool-size` option (default 20) so a cheap smoke test doesn't require classifying the entire 1,000-conversation subsample just to stay leak-free. The same review also caught "find the customer's root message and the brand's resolution" reimplemented three separate times, in the pipeline, the CLI, and the labeling tool, with inconsistent rules, so I consolidated that into `Conversation.root_customer_message()` and `Conversation.last_brand_message()` on the domain model, one definition instead of three that could quietly drift apart.

## Dataset subsample: 1,000 conversations, seed 42
Verified this against the raw 2.81 million row `twcs.csv` before committing to the number: union-find over the reply-chain columns finds 28,280 distinct connected conversation threads containing at least one SpotifyCares reply, so 1,000 is a genuine 3.5% random sample of the eligible pool, not the whole population. Each "conversation" here is the full connected thread, not just one inbound/outbound pair, so multi-turn resolutions stay intact for reply-grounding retrieval later. Those 1,000 conversations expand out to 3,436 total tweet rows. Picked this size to leave room for a golden set in the 150 to 250 range while staying cheap enough to reprocess with Haiku on every iteration.

## Subsample extraction lives outside src/, not inside adapters/dataset_twitter.py
The script that filters and samples down to `data/subsample/` is a one-time data-prep step, not something the runtime pipeline needs. `adapters/dataset_twitter.py` stayed an empty module in the first session on purpose, it got implemented later against the already-fixed subsample, keeping that first session's scope to scaffolding and data prep, none of the actual LLM-calling pipeline.

## API key loading: python-dotenv, wired into Settings.from_env()
`Settings.from_env()` used to read `ANTHROPIC_API_KEY` straight from `os.environ`, so a `.env` file on its own did nothing unless you exported it into every shell yourself. Added `python-dotenv`, one new dependency, about 20 lines, and a `load_dotenv()` call at the top of `from_env()`. `.env` (gitignored) holds the real key, `.env.example` (committed) is the template anyone else fills in. Simple, standard, keeps the secret out of shell history without asking a grader to set up a permanent env var.

## The Anthropic API costs money, and a $5 top-up covers this whole project
There's no ongoing free tier, just a one-time trial credit some accounts get, and this one didn't. I looked at switching to Gemini's actual free tier instead, but that meant a new adapter against a different SDK and structured-output mechanism, redoing the whole Haiku/Sonnet split, and living with daily request caps, all for the lowest-priority part of the grading rubric, the agent itself, against a six-day deadline. Paid the $5 minimum instead. Zero rework, and the architecture already routes the highest-volume call, classifying the roughly 1,000-conversation subsample for the precedent index, to cheap Haiku, while Sonnet stays reserved for the low-volume calls where quality actually matters, drafting and judging. Kept that split as-is instead of pushing everything down to Haiku, since the volume difference was already doing most of the real cost control.

## Judge-human agreement is computed on intent and escalate, not reply quality
The golden set schema only has true intent and true escalate, deliberately, to avoid anchoring, so there's no reference reply or quality score to compare against. "Judge-human agreement" here means Cohen's kappa between the pipeline's predicted intent and escalate calls and the human labels, not a comparison of the judge's reply-quality score against anything. The judge's score ends up as its own separate headline metric, mean reply quality across the golden set, with nothing external to validate it against, which is itself a good candidate for a "what's misleading" caveat: a high mean judge score could just mean the judge and the drafter share the same LLM-shaped notion of a good reply, not that an actual human would agree. Added `raw_agreement`, generic over the same `Hashable` pattern as `cohens_kappa`, to `domain/metrics.py` for the raw-versus-chance-corrected contrast on the escalate boolean, since `classification_accuracy` was typed to `Intent` only.

## The eval's precedent pool has to exclude golden conversations by name, not just by slice
Same class of bug as the earlier CLI leak: `eval/run_eval.py` builds the precedent index from every subsample conversation with the golden set's conversation ids explicitly filtered out first, not just some disjoint slice, since the golden set is a fixed seeded sample drawn from that same subsample and could otherwise overlap with whatever the precedent pool happened to include.

## Baseline design: baseline 1 skips the escalation policy entirely, baseline 2 reuses the real adapters with swapped settings
`evaluate_system` takes an `escalation_policy` that can be `None`, meaning "always auto-handle," which is baseline 1's actual behavior rather than routing a keyword classifier's made-up confidence through `decide_escalation` as if it meant something. Baseline 2, zero-shot ungrounded Haiku, isn't a new adapter at all, it reuses the real classifier (so its output shares a cache with the full agent's classification) and the real drafter, just with the Sonnet model swapped for Haiku and an empty precedent index, instead of a parallel drafter class written just for this. Baseline 1's keyword classifier reports a flat confidence of 1.0, since a rule match doesn't really have a notion of confidence, and that's fine only because `escalation_policy=None` means that number never actually gets read by anything.

## Concurrency, then a full review pass to make it safe
The sequential eval run against 83 real golden examples took long enough, over 500 chained API calls, to be a real, observed problem rather than a hypothetical one, so the `ThreadPoolExecutor` optimization I'd been deferring finally went in on both hot loops. An 8-angle review of that diff (7 angles actually ran, conventions was skipped since there's no CLAUDE.md in this repo) turned up 8 confirmed or plausible issues, all fixed:
- `ResponseCache` had a same-filename write race once two concurrent callers could share a cache key (plausible here, given how repetitive this dataset's messages are). Fixed at the root: `get_or_set(key, compute)` now holds a per-key lock across the entire check-compute-write sequence, closing both the corruption risk and the wasted duplicate API call in one move, and `set()` also writes to a uuid-suffixed temp file as extra insurance.
- `build_precedent_index` got the concurrency but not the same per-item failure isolation its sibling function got in the same diff. Fixed with the same isolate-and-skip pattern, a failed classify just costs one fewer precedent in that intent's bucket, low-stakes enough that a silent skip plus one summary line is the right amount of ceremony, unlike the eval harness's results, which get a full structured failure list since they're reported data.
- The keyword classifier's plain substring matching was false-positiving inside unrelated words, "charge" matching inside "charger," that sort of thing. Fixed with word-boundary regex matching.
- The classify and draft token caps carried the same truncation risk I'd just fixed for the judge and hadn't gotten around to yet, bumped both up and gave the classify prompt the same brevity instruction the judge prompt already had.
- Loading the golden CSV as plain utf-8 would crash on a BOM-prefixed file, a real risk if anyone ever opens and resaves it in Excel, and it was silently defaulting any unrecognized escalate value to False instead of actually validating. Fixed with `utf-8-sig` and an explicit check that raises on anything unexpected.
- `load_dotenv()`'s default behavior let a stale shell env var silently beat `.env`, and the README was still telling people to export the key, a self-inflicted footgun. Fixed the actual root cause, the conflicting instructions, rather than the override default, since a real env var silently losing to a stray `.env` file felt like the worse surprise. README now points at `.env` and calls out the precedence.
- `raw_agreement` and `classification_accuracy` had turned into the same algorithm written twice. `classification_accuracy` now just delegates to `raw_agreement` instead of getting deleted outright, keeping the already-documented public name intact.

Added a proper test file for the cache, including a 20-thread race test asserting the compute function runs exactly once for a shared key, plus coverage for the new word-boundary matching, golden-set validation, and precedent-index failure isolation, all pieces where correctness is genuinely arguable, per the project's own testing philosophy, not glue code.

## Judge max_tokens raised from 300 to 500 after a live smoke test caught it
A cheap end-to-end smoke test against the real API, just two real subsample conversations, caught the judge truncating mid-JSON on a longer rationale. Raised the cap to 500 and tightened the judge's system prompt to specifically ask for one or two sentences, so typical usage stays well under the new cap rather than just relying on the ceiling to save it. Caught by actually running the harness once against the live API on a throwaway sample before committing to a full labeling pass, not by any unit test, since this is exactly the kind of adapter-level failure unit tests structurally can't catch.

Also confirmed the spec explicitly allows keeping the repo private as long as access gets granted to the Hiver team, so going public isn't actually required, just one valid option among a couple.

## Closed the loop on both open decisions, with real before-and-after data
Three decisions were sitting open at the end of the last round. Rate the reply-quality sample: done, 30 real ratings collected. Keep the repo private until submission day rather than go public now: noted, no action taken. Add account_access to the escalation high-risk set: implemented.

**Judge-human reply-quality agreement**, computed against the 30 real ratings: Pearson correlation 0.41, a binary "good reply" kappa of 0.36 (fair), mean absolute difference of 0.70, agreement within one point 90% of the time. The mean human score, 4.17, and the mean judge score, 4.16, matched almost exactly, which on its own would look like a clean validation, but the per-example numbers tell a different story. Pulling the three biggest disagreements turned up three distinct, nameable mechanisms rather than random noise: the judge caught a genuinely garbled generated sentence that a human rated 5 out of 5 anyway, the judge missed that a reply claimed an unverified completed action ("we've sent you a DM") that never actually happened, which the human penalized, and the judge rewarded a procedurally correct but tone-deaf reply to a frustrated customer that the human marked down. This became the report's leading "what's misleading" finding, and it's the actual required evidence the assignment asks for.

**Escalation policy: added account_access to `Settings.high_risk_intents`.** Recomputed the predicted-escalate and escalation-reason columns for the full agent and baseline 2 locally, by replaying the escalation decision against predictions that were already classified and already cached, zero new LLM calls needed, since escalation is a pure function sitting on top of classification and the classification itself never changed. Confirmed this produces exactly what a live rerun would, and that the full agent and baseline 2's escalate columns stayed identical to each other afterward, same as before.

**Result:** escalate kappa went from 0.099 to 0.417, recall on true escalations from 23% to 59%, and precision improved too, from 56% to 71%, not a recall-for-precision tradeoff. 31 of the original 66 misses closed outright. The remaining 35 misses are 83% concentrated in playback_bug, a category that was never a high-risk candidate since most playback bugs really are low-stakes, which confirms the report's own earlier prediction that category-membership rules eventually hit a ceiling. This isn't a coverage gap more categories would fix, it's a severity-modeling gap.

Named the resulting caveat explicitly rather than letting the improved number stand there uncontextualized: the high-risk-set change came from looking directly at this exact golden set's own failure analysis, so the kappa jump is a real, measured result on this sample but wasn't yet confirmed to generalize. Added that to both the Problem Framing section and the top of "What I'd do differently." Rewriting a report to make its own biggest win sound a little less certain than it could is exactly the instinct this whole project is supposed to model.

Rewrote every part of REPORT.md that touched escalation numbers, the headline table, both the "what's misleading" and "results vs baselines" paragraphs, the failure-analysis section restructured into a clean before, fix, after, what's-left shape, the billing_dispute cross-reference, and "What I'd do differently," rather than leaving the old 66-miss story sitting next to the new numbers.

## Bootstrap confidence intervals, a golden-set methodology note, a report trim, and a held-out set
Closed one more gap found on a second read of the spec: "with a short note on how you sampled and labelled them" wasn't written down anywhere a grader would actually find it, only implied inside DECISIONS.md's schema reasoning and the labeling tool's code. Added an explicit note to README's Dataset section.

Built `eval/bootstrap_ci.py`: 2000 resamples over the existing eval data, computing 95% confidence intervals on intent kappa for both the full agent and baseline 1, and escalate kappa under both the old and new high-risk policy, plus a paired bootstrap run directly on the policy-change improvement itself (resampling the same 200 examples once per iteration and computing both policies' kappa on that same resample, rather than comparing two independently-resampled intervals, since the two policies are being scored on the same underlying data and a paired comparison is the statistically honest one here). Reused the actual escalation function to recompute the old policy's column on the fly from the already-cached predictions, no need to have kept a backup of the pre-fix file lying around. The result: the old policy's escalate-kappa interval is [-0.02, 0.23], it includes zero, meaning it was statistically indistinguishable from chance, not just numerically low. The new policy's interval is [0.29, 0.54]. The paired improvement interval is [0.21, 0.42], excluding zero, real, statistically supported evidence the fix helped, not just a point estimate that happened to move. Folded the sharpest of these into REPORT.md's "what's misleading" section and trimmed some of the surrounding prose in the same pass to make room, since the assignment caps the report at 6 pages and it was starting to push against that. Net length actually dropped despite adding real content.

Built `eval/label_holdout.py` (40 conversations, sampled disjoint from the golden set, seed 4242, writes to `data/golden/holdout_set.csv`, same resumable pattern as the original labeling tool) and gave `eval/run_eval.py` a `--golden-path` option, previously hardcoded, so the same already-tested evaluation pipeline could be pointed at the holdout set once it was labeled, instead of writing a near-duplicate script just for this. This is the direct answer to the caveat already sitting in REPORT.md: the account_access fix came from looking at the golden set's own failure analysis, so measuring it again on that same golden set proves nothing about whether it actually generalizes. Only a genuinely held-out sample can answer that.

## Held-out validation finished, and the fix really does generalize
Labeled all 40 held-out conversations and ran the full evaluation against them, all three systems, real API calls. Full agent results on the held-out set: intent kappa 0.402, close to the 0.412 the golden set gave, and escalate kappa **0.557**, actually better than the 0.417 the fix produced on the data that inspired it, with recall on true escalations at 15 out of 17 (88%) and precision at 15 out of 22 (68%). The improvement didn't just hold up, by this measure it held up even better, on data the fix had never seen before. Folded this straight into REPORT.md's failure analysis as a new paragraph, and updated the Problem Framing caveat and "What I'd do differently" to reflect that the out-of-sample check is actually done now, not just proposed, with the honest caveat that 40 examples still carries real sampling noise of its own and a bigger set would tighten these numbers further. `data/golden/holdout_set.csv` is now a real committed artifact with the same status as the golden set itself, genuine hand-labeled ground truth the report's claims depend on, not scratch data to throw away.

One thing worth noting but not chased any further: baseline 1's intent kappa came out noticeably higher on the holdout set, 0.422, than on the golden set, 0.183, with a 95% CI of [0.106, 0.265], so this result sits outside that interval. At n=40 that's plausibly just ordinary small-sample variance in which keywords happened to show up in this particular draw, baseline 1 is a fixed, deterministic ruleset, nothing about it actually changed between runs. Didn't dig further since baseline 1 is the least important of the three systems here, and this doesn't touch the actual question the holdout set was built to answer.
